## 2. 需求分析

### 2.1 业务背景

ITAM 多个功能页面需要上传/管理与业务对象相关的文件（合同扫描件、验收单、发票等）；同时资产等对象的属性变更需要完整、可追溯的变更历史。当前缺少统一的附件承载与统一的变更日志，导致文件散落、变更难以追溯。本需求提供三项通用能力：多功能页面附件、统一 Activity 日志、日志记录展示优化。

### 2.2 需求价值

#### 2.2.1 模块价值点

- **文件集中承载**：在出现附件的页面统一以右侧区块承载，支持多附件与全生命周期管理（上传/下载/重命名/删除/搜索/排序）。
- **变更可追溯**：统一 Activity 日志记录属性变更的时间、操作者、字段、前后值与变更渠道。
- **渠道可辨识**：按 Manual/导入/Workflow/API 四类渠道用不同颜色区分，Workflow 可跳转流程详情。
- **体验优化**：日志放在独立但易访问的位置，既不干扰主信息浏览，又提供完整历史追溯。

#### 2.2.2 调研结论及竞品分析

参考主流 ITAM/ITSM：对象详情页普遍提供 Attachments 与 Activity/History 区，变更记录区分手动与自动（流程/集成）来源。ITAM 在此基础上统一了四类数据渠道的可视化区分与流程实例跳转。

### 2.3 用户故事

- 作为**资产管理员**，我希望在资产/合同等页面上传并管理附件，以便集中留存相关文件。
- 作为**审计人员**，我希望查看资产属性的完整变更历史与来源渠道，以便追溯与合规。
- 作为**运维**，我希望日志支持筛选、搜索与排序，以便快速定位某字段的变化。

## 3. 需求设计

### 3.1 多功能页面附件

#### 3.1.1 涉及功能页面

硬件 资产、耗材 asset、软件 licenses、Bundled asset；规格（hardware/software/bundled/合同 规格/软件 规格）；Fixed asset、合同；Inventory（stockroom、stockroom type、stock rule）；Resource（location、cost center）；Organization（公司、供应商、制造商、Customer）；资产 Audit（Audit Template、Audit Plan、Audit Task）。

#### 3.1.2 涉及到的表

- `attachment`（附件表，记录文件名、大小、类型、上传人、上传时间、关联对象）
- 各业务对象表（asset、contract、fixed_asset、规格、stockroom、location 等，作为附件宿主）

#### 3.1.3 功能描述

| 需求点 | 需求描述 | 逻辑描述 |
| --- | --- | --- |
| 附件位置 | 统一放在出现附件的页面中 | 作为页面展示的一部分，固定占据页面右侧区块展示 |
| 上传文件 | 选择文档，在当前页弹窗提示上传 | 点击 Upload 后附件上传到系统并展示在当前页，可上传多个附件 |
| 文件大小限制 | 最大 100M | 超过给弹窗提示 `The File is too large, please choose again` |
| 支持格式与图标 | 上传支持格式以 UI 设计为准 | 文件展示 logo 参考设计稿（完整格式见附件设计稿） |
| 搜索附件 | 支持搜索已上传附件 | 按名称搜索命中展示 |
| 下载附件 | 支持下载已上传附件 | 可选择全部下载或单个下载 |
| 单个操作 | 对单个已上传附件操作 | 支持下载、删除、重命名 |
| 排序 | 对已上传附件排序 | 支持由近及远、由远及近排序 |

#### 3.1.4 字段说明（附件）

| 字段名 | 数据类型 | 长度 | 备注说明 |
| --- | --- | --- | --- |
| 文件名 | VARCHAR | 255 | 附件文件名，支持重命名 |
| 文件类型 | VARCHAR | 32 | 文件类型（以 UI 设计支持格式为准） |
| 文件大小 | INTEGER | - | 文件大小，上限 100M |
| 上传人 | VARCHAR | 32 | 上传人 |
| 上传时间 | TIMESTAMP | - | 上传时间，用于排序 |
| 关联对象 | VARCHAR | 64 | 关联的业务对象（资产/合同等） |

### 3.2 统一 Activity 日志

#### 3.2.1 功能描述

当 ITAM 中资产 Details 页属性信息发生变更时，记录所有变更日志，且日志展示在 Details 页面。

- **目标对象**：asset、contract、Fixed asset。
- **触发条件**：资产 Details 页中属性发生变更。

#### 3.2.2 涉及到的表

- `activity_log`（变更日志表，记录变更时间、操作者、字段、渠道、前后值、流程类型/编号）
- 目标对象表（asset、contract、fixed_asset）

#### 3.2.3 字段说明（日志记录）

| 字段名 | 数据类型 | 长度 | 备注说明 |
| --- | --- | --- | --- |
| 变更时间 | TIMESTAMP | - | 属性变更发生时间 |
| 操作者 | VARCHAR | 32 | 执行变更的用户/系统 |
| Field | VARCHAR | 64 | 变更字段，显示属性名称 |
| Data Channel | VARCHAR | 32 | 数据变更渠道：Manual/导入/Workflow/API |
| Change Content | TEXT | - | 显示变更前的属性字段值、变更后的属性字段值 |
| Workflow 类型 | VARCHAR | 40 | 流程类型，仅 Data Channel=Workflow 时展示（查询工单中包含的流程类型） |
| Workflow 编号 | VARCHAR | 40 | 流程实例编号，可点击进入流程详情页，仅 Data Channel=Workflow 时展示 |

#### 3.2.4 字段字典值说明

| 字段名 | 字典值 | 说明 |
| --- | --- | --- |
| Data Channel | Manual | 数据手动改变 |
| Data Channel | 导入 | 批量导入改变 |
| Data Channel | Workflow | 流程自动驱动改变（展示 Workflow 类型 / 编号） |
| Data Channel | API | 第三方 API 驱动改变 |
| 排序 | 排序 activity by oldest to newest / newest to oldest | 由远及近 / 由近及远排序 |

#### 3.2.5 展示与交互

- 在 Details 页最右侧增加日志 logo，点击后在右侧固定位置显示 Activity 日志信息。
- 不同记录根据数据变更通道给予不同颜色（四大类：手动/导入/流程驱动/API）。
- 一个固定时刻发生多个属性字段变更时的展示需同步考虑搜索展示（以设计稿为准）。
- **筛选**：点击筛选 logo 显示 字段变更，展开后显示可被更改的属性项名称；选择属性后仅展示该属性的变化历史（如仅展示 state 属性变化历史）。
- **搜索**：可输入任何日志值，无论属性或变更值，均可模糊匹配命中展示。
- **排序**：排序 activity by oldest to newest / newest to oldest，可由近及远、由远及近排序。

### 3.3 日志记录展示优化

- 改造当前日志记录展示：日志信息应放在一个独立但易于访问的位置，既不干扰主要信息浏览，又能提供完整的历史追溯（交互以设计稿为准）。

### 3.4 可能影响模块

- 需要考虑移动端适配问题。
- 日志审计：附件的上传/删除/重命名等操作按日志审计规范记录（操作者、时间、模块、操作按钮、内容、结果）。

## 4. 验收标准

- 附件区块在所列全部功能页面右侧固定展示；支持多附件上传（单文件 ≤100M，超限提示 `The File is too large, please choose again`）、搜索、全部/单个下载、单个下载/删除/重命名、由近及远/由远及近排序。
- 资产/合同/固定资产 Details 页属性变更时生成 Activity 日志，记录变更时间、操作者、Field、Data Channel、前后值；Workflow 渠道额外展示 Workflow 类型 与可点击跳转的 Workflow 编号。
- 日志按四类渠道用不同颜色区分；支持 字段变更 筛选、模糊搜索、双向排序。
- 日志展示位置独立且易访问，不干扰主信息浏览。
